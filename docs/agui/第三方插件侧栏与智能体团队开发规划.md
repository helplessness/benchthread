# 第三方插件侧栏与智能体团队开发规划

本文记录已确认的产品范围和实施顺序。下文的面板接口、授权界面和验收用例属于待实现设计。第一版的交付目标是让外部开发者用公开 SDK 写一个插件，在另一台装有 TCode 的机器上从本地包加载，用自己的界面驱动自己的 Agent 团队，全程无需修改 TCode 源码。

## 一、用户和开发者将得到什么

开发者可以从本地目录加载插件进行调试，再将同一份清单和资源打成一个包交给用户。用户从插件列表导入包，查看它提供的面板、公开 Agent 和权限，同意后加载。在列表里关闭加载开关即可停用，包仍保留在已安装列表中。未来分发平台沿用包格式和版本信息。首版只验收本地开发和本地导入，采用 TCode 自有规范。

| 包形态 | 作者提供 | 加载后的用户入口 |
|---|---|---|
| 纯界面 | 插件清单和构建好的静态资源，可用任意前端框架 | 二级侧边栏出现面板，无需 Python 占位入口 |
| 纯 Agent 或团队 | 公开 Agent 或协调者、成员定义，以及按需提供的工具和技能 | Agent 选择器出现公开入口，内部成员按声明隐藏 |
| 界面和团队组合 | 同一个包同时声明面板、团队及面板可调用的入口 | 用户可从面板启动或追问，也可在 Agent 选择器中主动选择团队 |

## 二、用「文献证据助手」定义交互

1. 在插件列表加载文献证据助手。用户从二级侧边栏打开面板，选择本地 PDF，输入“作者说这个突变提高了活性，依据在哪里？”。
2. 用户点击“查找证据”。宿主将文件引用和问题交给插件团队，阅读成员定位段落和表格，复核成员判断材料能支持什么结论。面板显示运行状态和证据卡。每张卡保留稳定条目标识、文件引用、页码、原文摘录和证据局限。未找到证据时显示缺口。
3. 用户选择某张卡点击“核对这一条”。团队收到该条目标识和来源，面板把复核结果显示在原卡下。分别选择两张卡应得到两个可追溯的复核对象。此步验证界面操作确实改变了 Agent 的工作对象。
4. 用户点击“带入对话”，宿主将选中项的摘要和可解析的来源引用关联到当前会话。用户接着问“这条证据能支持作者的结论吗？”，主 Agent 可以识别该条目，在授权范围内回读原文。其他卡片与团队日志仍留在面板。

证据卡的字段和渲染归插件所有。宿主只理解插件身份、运行、结果条目、来源引用和显式选中动作。相同接口也可承载文件中的一行数据或结构中的某个残基。

## 四、公开 SDK 需要约定什么

以下约定描述调用语义。实施时先对照现有 API，再确定方法名及版本，避免维护两套运行接口。

| 操作 | 插件可提交或收到的信息 | 宿主责任 |
|---|---|---|
| 注册面板 | 稳定面板 ID、标题、包内入口、可调用的团队入口 | 校验入口位于包内、团队归属、SDK 版本和当前加载状态 |
| 打开面板与文档 | 主题、会话变更通知、用户打开文件后取得的受控引用 | 绑定面板实例、工作区和会话。资源读取逐次校验，iframe 不持有宿主凭据 |
| 启动与追问 | 团队入口、问题、文件或选中项引用、唯一提交标识 | 创建独立运行并返回运行 ID。相同提交可重试，保持主聊天原有 Agent |
| 查询与恢复 | 按运行 ID 获取状态、结果和产物引用 | 校验归属，先返回已有快照再更新。重连和刷新只恢复已有运行 |
| 带入对话 | 经用户确认的条目标识、摘要、来源引用 | 把选择写入目标会话；校验过期引用和权限，避免把另一会话的选择写入当前会话 |

## 五、权限与 harness 行为

插件列表提供一个加载开关。详情页只列本插件申请的能力，按文件、Agent 与工具、会话数据、外部网络、命令执行分类，显示具体范围和用途。用户在安装时点击“同意并加载”，以后可逐项关闭。已授予范围内的重复操作自动批准。新增权限或扩大范围时提示用户确认。关闭可选权限只影响对应功能；缺少必需权限时在列表中说明加载受限原因。

文献示例的安装页只需说明三件事：读取用户在面板打开的文档、使用文献团队与 PDF 工具、将主动选中的证据带入当前对话。选文件和点击“带入对话”本身就是用户操作，无需重复弹窗。后端按文档引用及具体工具执行检查。权限撤销对后续受控调用立即生效。

| 用户操作 | 期望行为 |
|---|---|
| 从 TCode 切到 OpenCode 等外部 harness | 切换前提示插件将不可用，并提示当前进行中的插件任务。切换完成后，面板、Agent 和工具入口停止服务于该会话，后端拒绝来自该 harness 的插件调用。其他 TCode 会话维持原状态。 |
| 切回 TCode、重开面板 | 重新校验加载状态和授权，按原会话恢复运行。此前已受理的任务由原 TCode 运行继续跟踪。 |
| 重启 TCode | 恢复运行记录，核对实际执行状态。远程作业通过已有 Job Protocol 查询，本地执行已中断时提供明确状态与重试入口。 |
| 用户停止任务 | 按运行 ID 停止相应任务。远程取消以服务回执为准；等待回执时显示实际进度。 |
| 停用或卸载插件 | 移除入口，停止接受新调用。有进行中的任务时说明其状态和处置选项。已交付的宿主摘要和产物引用可从历史记录查看。 |

## 六、三阶段交付

| 阶段 | 实施与交付 | 阶段通过条件 | 初估 |
|---|---|---|---|
| 一、本地开发、安装与加载 | 扩展清单和包校验，支持开发目录与安装包；增加权限列表和加载开关，建立侧栏与公开 Agent 的发现机制。先用普通第三方包验证声明团队、访问选定文档的可行路径。 | 三种包分别加载成功；纯界面包无需 Python；已有插件照常加载；停用移除入口；开发目录与安装包使用相同授权规则。 | 2–4 人日 |
| 二、面板驱动团队 | 建立面板与宿主通信，接入团队提交、恢复、复核选中项与带入对话；接入会话切换、授权撤销和 harness 校验。完成文献证据助手。 | 用同一 PDF 连续复核两个条目，条目与页码正确；刷新无重复任务；主聊天并行可用；切换 harness 后访问受限且切回可恢复。 | 4–7 人日 |
| 三、独立安装与开源验收 | 交付中文开发指南、最小模板、可打包示例与包校验说明。在干净工作区分别走 Web 和桌面端本地安装流程。 | 外部作者只用公开 SDK 和文档即可生成插件包；普通用户能安装、授权、运行、撤权和卸载。记录宿主版本、包版本、实际结果与未通过项。 | 2–3 人日 |

合计约 **8–14 人日**，按一名熟悉项目的开发者估算。前提是宿主能复用既有团队运行和状态记录。若阶段一发现隔离包的团队发布、并行运行或恢复需要调整底层运行时，先记录缺口并重估阶段二。

## 七、验收中必须覆盖的失败路径

| 风险 | 验证动作与预期结果 |
|---|---|
| 演示依赖官方信任 | 使用普通第三方包在干净工作区测试，不加入受信名单。文档读取和团队调度均能经宿主完成。 |
| 跨会话或跨插件读取 | 用两个会话、两个插件交叉引用运行 ID 和文件引用。宿主拒绝越权请求；切走会话后晚到的结果归回原运行。 |
| 丢回执造成重复提交 | 在宿主已受理后模拟断连，重新进入面板。原提交恢复为同一运行，后台只有一份任务。 |
| 插件操作干扰主聊天 | 主聊天运行中启动插件团队，再停止插件任务。主聊天的 Agent、运行和消息归属保持正确。 |
| 权限撤销只影响按钮 | 撤销读文档权限后，从仍打开的面板重新请求文件。后端拒绝新读取，并向用户说明原因。 |
| 选中项随列表排序漂移 | 先选一张卡，再重排卡片并复核；核对 Agent 接收的条目标识、文件和页码。主聊天只接收用户明确带入的条目。 |

最终验收使用可在本地读取、内容与页码可人工核对的 PDF。记录安装授权、侧栏操作、对应运行 ID、两次选中项、会话追问和重开结果。自动测试与真实界面验收分别记录；远程 MCP 不作为本示例的依赖。
